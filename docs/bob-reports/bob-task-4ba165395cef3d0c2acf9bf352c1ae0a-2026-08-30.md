# Fix the Node.js GitHub repository test execution pipeline in ReleaseGuard.

I tested ReleaseGuard against:

https://github.com/expressjs/express.git

ReleaseGuard correctly detects the repository as NODE and selects `npm test`, but the UI shows:

Tests: 0
Passed: 0
Failed: 0
Findings: 0
RELEASE READY

This is incorrect and unsafe.

Analyze and fix the complete pipeline.

REQUIRED FIXES:

1. NODE DEPENDENCY INSTALLATION

In releaseguard/runners/runner.py, add deterministic Node dependency installation before running tests.

For Language.NODE:

- Resolve the detected project cwd first.
- If package-lock.json exists, run:
  npm ci
- Otherwise, if package.json exists, run:
  npm install
- Run the install command in the project's actual cwd.
- Use subprocess.run with captured stdout/stderr and a reasonable timeout.
- Do not silently treat installation failure as successful test execution.
- If dependency installation fails, return a TestRunResult that causes a HIGH TOOLING finding or execution failure finding.
- Never continue to RELEASE READY after a dependency installation failure.

Python dependency behavior should remain unchanged.

2. FIX NON-ZERO TEST COMMAND HANDLING

In releaseguard/analyzer/rules.py, fix `_rule_tests_failed`.

The current early return:

    if not run.has_failures:
        return []

causes a serious bug.

A command can exit non-zero even when the parser cannot determine failed test counts.

Implement safe deterministic behavior:

- If run.exit_code != 0 AND parsed failed count is unavailable or zero AND total test count is unknown, create a HIGH TESTING finding.
- Title should clearly indicate that the test command exited non-zero and test execution could not be verified.
- Include exit_code and captured stdout/stderr evidence.
- This case must prevent RELEASE READY.

Only create the BLOCKER functional finding when actual failed tests are known.

3. ZERO/UNKNOWN TEST SAFETY

Ensure these cases NEVER result in READY:

CASE A:
exit_code != 0, total is None, failed is None or 0

CASE B:
exit_code == 0, total == 0

CASE C:
exit_code == 0, total is None

Each case must produce a HIGH or BLOCKER finding.

4. NODE PARSER

Keep support for:

- Node built-in test runner
- Jest
- Mocha

Do not regress existing parser behavior.

Ensure Mocha output such as:

  100 passing
  2 failing

correctly produces structured totals.

5. ADD REGRESSION TESTS

Add tests covering:

- Fresh Node project with package-lock.json → npm ci is attempted before npm test
- Node project without package-lock.json → npm install is used
- Dependency installation failure produces a finding and blocks READY
- Non-zero npm test with unknown/unparseable output produces a HIGH finding
- exit_code 0 with total None produces HIGH finding
- exit_code 0 with total 0 produces HIGH finding
- Valid Node built-in test output parses correctly
- Valid Mocha output parses correctly
- A successful Node project can still become READY

6. RELEASE SAFETY

The final policy must never allow:

non-zero test execution
zero verified tests
unknown test execution

to result in RELEASE READY.

2. If installation fails → `unavailable_reason` is set → `_rule_tooling_unavailable` emits `HIGH TOOLING` → decision is `REVIEW_REQUIRED`, never `READY`

4. If `npm test` exits non-zero with parsed failure counts → `BLOCKER FUNCTIONAL` finding → `BLOCKED`
5. Only a clean `npm test` with parsed counts > 0 and exit_code 0 can produce `READY`
